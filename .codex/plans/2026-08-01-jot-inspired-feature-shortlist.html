Open Decisions

Goal and Scope

Outcome

  • A viewer can sign in once and find the team apps they may open.
  • An agent can publish a self-contained HTML result with one deploy command.
  • Optional local counters show an app owner whether an app is being used.

Non-goals

  • No executable app backend or outbound-network escape hatch.
  • No public mode, external invitations, per-viewer records, or sensitive-data positioning.
  • No custom database, analytics service, or second listener.

Principle gate

Strengthens Principles 12, 14, 16, and 17. Every catalog read remains behind the global identity broker and every app open still re-enters the normal app-host authorization path.

Logic and Data Flow

P0 — Team catalog

  1. Viewer completes the existing platform OTP flow; the server reads the opaque global identity.
  2. GET /apps asks persistence for active apps whose current owner/email/domain policy matches the server-derived identity.
  3. The query returns only slug, active deployment description/tags, and server-derived stable URL. Missing/corrupt policy excludes the app.
  4. The server renders the complete bounded list. Existing local JavaScript filters only the already-authorized cards.
  5. Opening a card visits the app hostname; the existing handoff and app-host session path rechecks policy before serving bytes.

P1 — Single-file publish

  1. CLI resolves the exact regular file with Lstat; symlinks and non-HTML inputs deny.
  2. CLI derives the slug from the filename when lossless and available, otherwise requires --as.
  3. CLI creates an in-memory canonical manifest and archive containing only index.html; relative external assets are not discovered or bundled.
  4. The normal authenticated upload, validation, activation, anonymous denial probe, and JSON result run unchanged.
  5. The immutable server deployment remains the durable receipt; JSON output includes the canonical inferred values.

P2 — Usage summary

  1. After an authorized response, a bounded counter records app ID, day bucket, request count, response bytes, and last activity.
  2. Flushes are bounded and failure never affects serving or authorization.
  3. Dashboard reads only aggregates for owned apps; no SDK capability is added.

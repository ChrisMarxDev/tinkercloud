Implementation plan TinyHost Updated 2026-07-28 12:26 CEST Planning only — no publication authorized

One signed release, several thin installation channels

Make the browser SDK natural in every TypeScript ecosystem and make the unprivileged tiny workstation CLI the front door for deployer work, operator administration, verified host bootstrap, health-gated self-update, and explicit client/server compatibility—without moving privileged server code or root authority into the client.

Recommended first user-observable M5 slice: an operator installs tiny on a workstation, runs tiny host install root@HOST --config host.yaml, and the CLI verifies, transfers, and invokes the signed tinyhost installer through strict host-key-checked SSH. The same CLI remains the deployer tool and later gains operator-only HTTPS commands.

Principles, Trust Boundary, and Ownership

Decision gates

  • Principle 6: an update cannot extend stale authorization or keep superseded live connections alive; reconnect reauthorizes against the new service.
  • Principle 7: tags, release assets, registry versions, and formula checksums are immutable; “latest” is only a signed pointer.
  • Principle 8: tinyhost remains one server binary; package managers distribute the smaller tiny client.
  • Principle 10: every installer and adapter has deny-path evidence before a happy-path publication.
  • Principle 14: all channels adapt one artifact set instead of building channel-specific implementations.
  • Principle 15: update restarts may drop live events; SDK clients reconnect, renegotiate, and reread current KV state rather than expecting replay.
  • Principle 16: canonical skills and their marked copies change with installation and verification guidance.

Trust boundary

The release boundary begins at the reviewed tag and external Ed25519 authority. Host bootstrap adds a second explicit boundary: the operator’s OpenSSH client, pinned known_hosts entry, and root SSH account. tiny may orchestrate that authority but never stores a private key, accepts a host key automatically, or converts a TinyHost bearer into root access.

The package registries, tap Git history, HTTPS endpoint, and package-manager integrity checks are additional delivery authorities. The signed release manifest remains the canonical byte identity and every adapter must prove equality to it.

Data ownership

Maintainers own registry scopes, tap repository, release domain, protected environments, and channel promotion. Operators own SSH/root authority, host profiles, server installation, and recovery. TinyHost owns operator/deployer authorization at the control plane. Deployers own only their app-scoped workflows and credentials. A person may hold both roles, but each command still selects and proves one authority path.

Logic and Data Flow

Release production and promotion

Install-time client flow

request exact version or resolve signed stable channel
→ detect supported OS/architecture locally
→ construct immutable release URLs (no redirects)
→ download payload + metadata + signature with size/time bounds
→ verify checksum and Ed25519 signature
→ stage beside destination
→ atomically replace tiny
→ run tiny version only after replacement
→ retain old binary on every pre-replacement failure

tiny host install flow

operator selects a named host profile or supplies SSH target + pinned known_hosts
→ tiny invokes system ssh in strict host-key mode for read-only OS/architecture/preflight facts
→ resolve exact signed TinyHost release locally
→ download and verify server binary, metadata, signature, and local installer
→ create a random root-owned remote staging directory through fixed SSH command
→ copy only verified artifacts plus operator-selected local secret files
→ remotely re-verify modes, ownership, artifact signature, and supported host
→ invoke the root-local installer, then signed tinyhost init
→ stream redacted structured progress back to tiny
→ run public health + anonymous-denial probes
→ remove remote staging secrets/artifacts
→ save only non-secret host profile metadata after success

The CLI orchestrates; it does not absorb server installation logic. Secret values are never command-line arguments, environment echo, logs, or profile fields. Cancellation or SSH loss leaves the signed binary’s resumable init state as the recovery source.

tiny operator 
tiny loads a platform-scoped CLI bearer from the OS credential store
→ call a typed /api/v1/operator/* endpoint over verified HTTPS
→ server authenticates credential type and rechecks current operator role
→ authorize exact operation and target
→ validate confirmation + idempotency
→ execute existing domain service transaction + redacted audit event
→ return bounded read model or stable safe error

Host-root operations never use the HTTPS operator bearer. Operator control-plane operations never invoke SSH or gain root. This is the key separation that keeps Principle 11 intact.

Signed self-update flow

tiny host update invokes root-local tinyhost update through strict SSH
→ read installed server/package/API/schema versions and active deployment requirements
→ resolve signed stable or exact candidate release
→ verify artifact + signed compatibility manifest before snapshot or stop
→ evaluate supported OS/architecture, upgrade-from range, database schema transition,
  migration rollback class, active app API requirements, and configured release origin
→ deny with an actionable compatibility report if any requirement is ambiguous or unsupported
→ download and verify complete candidate bytes
→ create bounded binary/state rollback snapshot
→ drain control requests and close live connections with a restart reason
→ stop service, apply binary and compatible migration, restart
→ verify local listener, executable diagnostics, exact running version/schema,
  public HTTPS version contract, and authenticated + anonymous-denial gateway probes
→ commit update and delete rollback snapshot, or restore prior binary/state and restart

“Self-update” means the signed tinyhost binary owns verification, migration, activation, health, and rollback. Root authority starts it locally or through tiny host update. The unprivileged long-running service never grants itself permission to overwrite its executable.

Client/server compatibility flow

tiny login or command:
  fetch public bounded compatibility document
  → compare tiny package + control API versions
  → send both version headers
  → server authenticates, rechecks compatibility, then dispatches or returns typed 426

SDK HTTP request:
  gateway authenticates app session
  → protected dispatcher validates SDK package + app API headers
  → dispatch or typed TinyVersionIncompatibleError

SDK WebSocket:
  authenticate before upgrade
  → negotiate live protocol + SDK version via bounded Sec-WebSocket-Protocol values
  → upgrade only when compatible; reconnect repeats authorization and negotiation

Server update:
  compare candidate support matrix with immutable active deployment app_api requirements
  → block activation if any active app would become unsupported
  → workstation CLIs not currently connected are handled on their next version negotiation

The server cannot inventory every CLI installed on someone’s laptop. It guarantees runtime negotiation for each request and pre-update compatibility for active deployed apps whose immutable manifests it owns.

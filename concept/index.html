Reconciled implementation concept · July 2026

A private app gateway that happens to deploy apps.

Tinkercloud lets one technical operator provide a safe, self-hosted deployment destination to people and agents who should not need to understand infrastructure or implement authentication.

No private app file, API, socket, blob, or backend request is reachable until Tinkercloud has authenticated and authorized it.

A human starts with the intended outcome. Tinkercloud asks only for information it cannot discover or safely default; generated config is a receipt, not prerequisite paperwork.

Reason for existing

Move the hardest recurring requirement outside generated apps

Small internal and client-facing apps are cheap to create but surprisingly expensive to expose safely. Authentication is repeated, inconsistently implemented, and easy for AI-generated software to omit. Tinkercloud makes privacy a property of the hosting boundary, independent of app framework or developer discipline.

The smallest compelling experience is one command that returns a protected URL and verifies that anonymous requests receive no app bytes.

North star: Shopify Quick's folder-to-secure-URL, client capability APIs, bundled agent skills, and “keep it simple, embrace the constraints” philosophy—adapted to Tinkercloud's stricter per-app authorization model.

V1 scope

One protected static loop

  • One tinkercloud server binary on a clean Hetzner VPS.
  • A separate small tinker deployer CLI.
  • Operator control plane with one exact active-deployer allowlist.
  • Persistent deployer CLI login, remembered verified server, account switching, and real logout.
  • Resend email OTP, one admin-host global browser identity, current dashboard-role checks, and policy-checked app-bound handoffs into isolated app sessions.
  • Private-only email/domain policy with implicit owner access.
  • Deploy-first manifest generation, immutable static releases, descriptions, activation, and failed-activation preservation.
  • Current-user, bounded JSON KV, lightweight local blobs, and ephemeral realtime APIs.
  • First-class TypeScript SDK and capability discovery.
  • Search/status filtering, safe app launch, hard app deletion, audit, quotas, signed server self-update/rollback, and diagnostics.

Non-goals

Do not become a PaaS in V1

  • No arbitrary backend processes or containers.
  • No custom domains, teams, billing, or marketplace.
  • No multi-node clustering or external database.
  • No public object URLs, remote blob backend, or browser secrets.
  • No mounted object store, per-viewer blob ACL, or durable/multi-node realtime in V1.
  • No operator backup/disaster recovery in the first release.
  • No provider secrets, LLM/Jira adapters, or arbitrary proxy in V1.

Implementation sketch

A modular monolith with one typed security transition

Public request→ Canonical host→ Active app→ App session→ Current policy→ AuthorizationContext→ Protected dispatcher
App URL→ App-bound handoff→ Platform identity or OTP→ Current app policy→ Host-only app session

Gateway

Owns public listeners, canonical host routing, app resolution, session validation, current policy, and dispatcher composition.

Deployment

Streams into staging, treats archives as hostile, creates immutable releases, atomically activates, probes denial, and restores the prior release on failure.

Persistence

SQLite holds authority and metadata; a private data directory holds immutable release bytes. Durable intermediate states bridge database and filesystem operations.

Client SDK

A small typed SDK is the primary app-development surface for identity, KV, ephemeral realtime, capability discovery, and future operator-governed integrations.

Open questions

Remaining evidence questions, not reopened decisions

  1. Which smallest Hetzner plan passes the complete V1 resource and failure-injection suite with useful headroom?
  2. Which project-output and SDK-usage signals are reliable enough for the deploy wizard to derive rather than ask?
  3. Does no-echo secret ingestion meet the supported-shell audit, or should guided setup always create/consume a protected file?
  4. Which remaining CLI and setup prompts fail the “necessary, unknown, unsafe to default” test?

Do or don’t

Build the secure static slice; defer the general runtime

Do: The problem is concrete, the structural solution is differentiated, and the secure static slice has high value for internal tools, review apps, dashboards, and AI-generated interfaces.

Don’t: Adding backend execution, remote/public blob infrastructure, durable realtime, custom domains, and organization features before the deployment denial proof would multiply attack surface and delay the defining user value.

Decision basis: impact 5/5, full-concept complexity 5/5, scoped V1 yield 4/5, primary risk severity 5/5. Proceed only with evidence-gated milestones, the gateway invariant, and minimum-necessary human flows as release blockers.

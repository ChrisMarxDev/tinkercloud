Implementation concept · July 2026

A private app gateway that happens to deploy apps.

TinyHost lets one technical operator provide a safe, self-hosted deployment destination to people and agents who should not need to understand infrastructure or implement authentication.

No private app file, API, socket, blob, or backend request is reachable until TinyHost has authenticated and authorized it.

Reason for existing

Move the hardest recurring requirement outside generated apps

Small internal and client-facing apps are cheap to create but surprisingly expensive to expose safely. Authentication is repeated, inconsistently implemented, and easy for AI-generated software to omit. TinyHost makes privacy a property of the hosting boundary, independent of app framework or developer discipline.

The smallest compelling experience is one command that returns a protected URL and verifies that anonymous requests receive no app bytes.

North star: Shopify Quick's folder-to-secure-URL, client capability APIs, bundled agent skills, and “keep it simple, embrace the constraints” philosophy—adapted to TinyHost's stricter per-app authorization model.

V1 scope

One protected static loop

  • One tinyhost server binary on a clean Hetzner VPS.
  • A separate small tiny deployer CLI.
  • Operator and deployer control plane.
  • Resend email OTP and app-scoped sessions.
  • Private-only email/domain policy with implicit owner access.
  • Immutable static releases, activation, and rollback.
  • Current-user, bounded JSON KV, lightweight local blobs, and ephemeral realtime APIs.
  • First-class TypeScript SDK and capability discovery.
  • Audit, quotas, signed self-update/rollback, and diagnostics.

Non-goals

Do not become a PaaS in V1

  • No arbitrary backend processes or containers.
  • No custom domains, teams, billing, or marketplace.
  • No multi-node clustering or external database.
  • No public object URLs, remote blob backend, or browser secrets.
  • No mounted object store, per-viewer blob ACL, or durable/multi-node realtime in V1.
  • No operator backup/disaster recovery in the first release.
  • No provider secrets, LLM/Jira adapters, or arbitrary proxy in V1.

Implementation sketch

A modular monolith with one typed security transition

Public request→ Canonical host→ Active app→ App session→ Current policy→ AuthorizationContext→ Protected dispatcher

Gateway

Owns public listeners, canonical host routing, app resolution, session validation, current policy, and dispatcher composition.

Deployment

Streams into staging, treats archives as hostile, creates immutable releases, atomically activates, probes denial, and restores the prior release on failure.

Persistence

SQLite holds authority and metadata; a private data directory holds immutable release bytes. Durable intermediate states bridge database and filesystem operations.

Client SDK

A small typed SDK is the primary app-development surface for identity, KV, ephemeral realtime, capability discovery, and future operator-governed integrations.

Open questions

Resolve with bounded spikes, not incidental code

  1. Does per-host HTTP-challenge ACME meet creation rates and operational simplicity, or is a manual wildcard escape hatch required?
  2. Which CGO-free SQLite driver meets performance, migration, update-rollback, and security requirements under real concurrent workloads?
  3. What exact Linux file-opening primitives guarantee beneath-root, no-symlink behavior across supported distributions?
  4. Should a failed post-activation public denial probe automatically roll back, quarantine the entire app, or both?
  5. What operator recovery credential and ceremony work when email is unavailable without creating a second remote auth bypass?
  6. Which CSP defaults remain useful for arbitrary static apps without creating false confidence?
  7. Which concrete Quick API conventions should TinyHost preserve, and where should stricter authorization remain visibly explicit?

Do or don’t

Build the secure static slice; defer the general runtime

Do: The problem is concrete, the structural solution is differentiated, and the secure static slice has high value for internal tools, review apps, dashboards, and AI-generated interfaces.

Don’t: Adding backend execution, remote/public blob infrastructure, durable realtime, custom domains, and organization features before the deployment denial proof would multiply attack surface and delay the defining user value.

Decision basis: impact 5/5, full-concept complexity 5/5, scoped V1 yield 4/5, primary risk severity 5/5. Proceed only with evidence-gated milestones and the gateway invariant as a release blocker.

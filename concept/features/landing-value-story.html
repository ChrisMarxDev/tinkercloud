Explain the private-web promise before listing the platform.

Keep Tinkercloud's playful cream, grape, cobalt, rounded type, cloud mark, and friendly illustrations. Rebuild the story around one concrete outcome: a deployer or coding agent turns a folder into a trusted team URL on one operator-controlled VPS.

Summary

Make the first screen answer four questions

  1. What is it? A self-hosted private web for small apps.
  2. Who is it for? Teams whose deployers and agents create tools, prototypes, reports, and demos.
  3. What happens? One command turns a folder into a stable HTTPS URL.
  4. Why trust it? Tinkercloud owns sign-in, access policy, activation, and the public gateway on one VPS the operator controls.

Reason and value

The current page looks trustworthy before it sounds specific

The existing hero is distinctive and correctly emphasizes private by default, open source, the operator's VPS, and the folder-to-URL flow. Its headline—“Your small apps. Securely shared.”—states a benefit but leaves the category, primary audience, and reason for choosing Tinkercloud to the supporting paragraph. The lower page then shifts quickly into a capability inventory.

A clearer story should let an operator or deployer recognize their situation immediately: agents make useful web artifacts quickly, but safely publishing, finding, and learning from them still requires repeated infrastructure work. Tinkercloud moves that work into one understandable system.

Scope

  • Rewrite the hero around category, audience, action, and trust.
  • Replace the decorative command pill with a reusable terminal-result scene.
  • Reorder the page from value proof to product mechanics.
  • Group technical capabilities by the work they remove for deployers and operators.
  • Add concrete generated-work examples: reports, prototypes, dashboards, review tools, forms, games, and small utilities.
  • Add an explicitly labeled “coming next” bridge to catalog discovery, public static publishing, and local insights.
  • Strengthen GitHub/setup calls to action and the single-binary explanation.

Non-goals

  • No visual rebrand, dark editorial clone, or replacement of the cloud mark.
  • No claim that public apps, catalog search, or local insights are available before their exit evidence exists.
  • No anonymous SDK capability, backend runtime, public upload, or second listener.
  • No invented customer logos, fabricated usage numbers, or fake live examples.
  • No external analytics script, remote font, tracking pixel, or new marketing backend.
  • No broad site architecture or documentation rewrite in the first slice.

Proposed content architecture

Lead with the outcome; reveal the platform in layers

  1. Hero — category and result. State the private-web promise, name teams and agents, show the real deploy command and returned protected URL, then offer “See one deploy” and “View on GitHub.”
  2. Why Tinkercloud — four decision reasons. Private by default, simple by default, made for generated work, and self-hosted as one understandable system.
  3. What one deploy removes. Explain built-in sign-in, access policy, immutable activation, TLS, storage, and live updates as work the deployer does not repeat.
  4. What teams make. Use concrete artifact cards rather than generic feature icons. Every example should name a recognizable job and the person who benefits.
  5. One VPS, honest limits. Show why the constraint improves operability and state clearly that V1 is for replaceable tools and prototypes.
  6. Coming next — reach and insight loop. Label catalog, public static publishing, and local 30-day insights as planned until each slice ships; link to no executable control.
  7. Close — choose the next action. Point operators to setup and deployers to the first-app path without making them decode role terminology.

Copy direction

A concrete first-screen draft

Hero thesis

Self-hosted · private by default · agent-ready

Turn small apps into trusted team tools.

Your team and coding agents create dashboards, prototypes, reports, and utilities. Tinkercloud gives each one a stable private URL, built-in access, and useful app capabilities—on one VPS you control.

Decision reasons

  • One deploy: a folder becomes a protected HTTPS URL.
  • Private by default: Tinkercloud checks access before serving app bytes.
  • Made for generated work: agents and deployers use the same narrow command and SDK.
  • Your system: one binary, one VPS, one place to understand and recover.

The exact final copy should be tested against operators and deployers. Do not use “user” where authority or setup responsibility depends on the role.

Terminal visual system

Show the command, the trust proof, and the result together

Deploy a private team app

$ tinker deploy ./dist --allow '*@acme.com'

✓ release activated
✓ anonymous access denied
✓ allowed viewers: *@acme.com

Private URL  https://launch-map.apps.acme.com
  • Use a deep-grape terminal surface, cream text, cobalt prompt, mint success, and yellow in-progress accents so it belongs to Tinkercloud.
  • Use one shell-safe, contract-backed command. The wildcard allow rule must be quoted so the shell cannot expand it.
  • Animate only one purposeful sequence: command, verification, URL. Respect reduced motion and show all content immediately when motion is disabled.
  • Add copy controls for the command and URL, visible keyboard focus, an accessible live status, and a persistent text label instead of color-only state.
  • Reuse the same component for future setup and public-publishing examples; never style unshipped commands as runnable.
  • Derive every displayed status line from stable CLI fixtures or documentation contracts before implementation.

Implementation sketch

Four bounded passes

  1. P0 — Message and hero proof. Update the landing copy contract and rendered-HTML tests; implement the hero thesis, role-aware CTA labels, and accessible terminal receipt using only currently shipped behavior.
  2. P1 — Story and examples. Reorder the lower page, replace the capability-first grid with decision reasons and concrete use cases, retain the SDK proof, and tighten the one-VPS/honest-limits section.
  3. P2 — Reach roadmap bridge. Add a clearly planned section for team catalog, public static publishing, and local insights. Promote each item from “coming next” to “available” only after its contract, deny matrix, deployment proof, and UI exit evidence pass.
  4. P3 — Public proof. After the public-static pilot, replace illustrative use cases with real first-party examples and link to them. Use Tinkercloud's own bounded local insights for those apps; do not add third-party marketing telemetry.

No deployment, trust, persistence, or public-interface decision changes in P0/P1. The landing remains a Cloudflare Worker marketing boundary with no authority over the Tinkercloud gateway or app data.

Acceptance criteria

  • In a five-second comprehension test, at least four of five participants can say that Tinkercloud self-hosts small team apps, makes them private by default, and deploys them with one command.
  • The first viewport names the audience, operator ownership, deploy action, protected URL outcome, and primary next action.
  • The terminal command is shell-safe, matches the CLI contract, and displays no status the real deploy path cannot prove.
  • Current and planned capabilities are visually and verbally distinct; no planned feature is presented as shipped.
  • At 390 px and 1440 px, the headline, terminal, URL, and CTAs have no clipping or horizontal overflow.
  • Heading order, keyboard focus, copy controls, status announcements, contrast, and reduced motion pass targeted accessibility checks.
  • Rendered-HTML tests assert the thesis, current/planned labels, shell-safe command, honest limits, and working navigation targets.
  • Production build, lint, deployment dry run, GitHub action, and public HTTPS content verification pass.

Open questions with recommended defaults

  • Primary audience? Write for deployers and coding agents first; reassure operators with one-VPS ownership and recovery. Viewers need no marketing-page path.
  • Primary CTA? Use “See one deploy” until the repository and installer are genuinely ready for first-time operators; keep GitHub as the secondary proof/action.
  • Public reach in the hero? Not yet. Keep the hero's shipped promise private; describe public-static publishing in a clearly planned section until L3 exits.
  • Show real examples now? Use named illustrative jobs without fake links. Replace them with first-party live examples at L4.
  • Animated terminal? Yes, once, under four seconds, with reduced-motion and static fallbacks. Clarity must not depend on the animation.

Do or don't

Do the message-and-terminal refresh before a broader visual redesign

Do: The plan has high yield because the current visual foundation is already distinctive and responsive. Copy hierarchy, command proof, and content order can materially improve comprehension without changing the product boundary or rebuilding the brand.

Don't: clone Jot's editorial appearance or advertise its broader runtime model. That would discard Tinkercloud's recognizable identity, confuse private/public availability, and weaken the explicit gateway and fixed-capability story that differentiates the product.

Concept decision: clarify the shipped private-web promise now, stage public reach honestly, and make the verified terminal receipt the landing page's signature.

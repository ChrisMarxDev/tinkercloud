Accepted post-V1 extension · governed by PRD §21.3 and ADR 0054

Share privately by default. Publish publicly on purpose. Know whether anyone came.

Extend Tinkercloud's agent-to-team loop with a searchable app catalog, deliberately public static deployments, and the smallest useful local analytics: visitors, page views, and last activity.

Public reach without a public backend runtime, remote analytics service, or accidental capability access.

Summary

Turn finished team experiments into public proof

Tinkercloud already makes a folder into a protected app URL. This concept adds the next loop: find the team's apps, explicitly promote a safe static app to the public internet, and see whether people actually visited it. Public apps remain ordinary immutable releases behind the same gateway; they do not gain server code, public data APIs, credentials, or a new listener.

Reason and value

Sharing creates the marketing loop that private hosting cannot

For deployers

An agent can build a demo, visual story, game, calculator, or launch page and publish the reviewed result without moving it to a second hosting product.

For teams

A signed-in viewer gets one searchable shelf of apps they may use, instead of collecting private URLs in chat and documents.

For operators

All publishing and analytics remain local to the existing gateway, database, domain, and operational surface.

Competitive evidence points in the same direction: Shopify Quick demonstrates broad creation when sharing is effortless; ChatGPT Sites pairs public publishing with basic traffic analytics; Jot pairs private team publishing with public slugs and local usage counters. Tinkercloud should adopt the loop while retaining its fixed capability model.

Scope

  • A viewer-facing catalog at the admin host showing only active apps the current identity may open.
  • Immutable manifest tags used for catalog display and local search.
  • An explicit public access mode for static files and SPA fallback.
  • A global operator gate, disabled by default, that permits public policies without making any app public itself.
  • Explicit deployer confirmation when a private app becomes public.
  • Default noindex; deliberate per-app search indexing opt-in.
  • Local daily page views, approximate visitors, and last activity.
  • Owner/operator dashboard summaries for 7 and 30 days.

Non-goals

  • No server.ts, workerd, backend process, function, cron, job, or arbitrary request handler.
  • No anonymous KV, collections, blobs, realtime, identity, or LLM capability access.
  • No public blob URLs, public uploads, public WebSockets, or anonymous write surface.
  • No custom events, funnels, heatmaps, referrers, paths, geography, devices, ad attribution, or session replay.
  • No external analytics script, product telemetry upload, or second persistence service.
  • No custom domains, external signed invitations, comments, public directory, or deployer-selected rollback in this concept.
  • No claim that approximate visitors equal people, accounts, or unique humans.

Public deployment experience

Public is a reviewed policy state, never a convenience flag that skips the gateway

# Operator enables the capability for this Tinkercloud host.
sudo tinkercloud public enable

# Deployer deliberately requests public static access.
access:
  mode: public
  indexing: false

features:
  kv: false
  blobs: false
  realtime: false

capabilities:
  llm:
    chat: false

tinker deploy .

Access broadening: anyone on the internet can open this app.
Publish demo publicly? [y/N]
  • The operator gate defaults off and is revisioned and audited. Enabling it permits requests; it changes no app policy.
  • A deployer must own the target and request access.mode: public. The server rejects public activation while any browser capability is enabled.
  • Interactive deployment asks once only when the effective policy broadens. Deterministic/JSON deployment requires an explicit machine-readable confirmation.
  • Turning the operator gate off removes anonymous access on the next request. Existing owner/email/domain rules remain available through the normal private login path.
  • Changing the app back to private removes anonymous access on the next request and does not wait for caches to expire.

Public request boundary

A typed public-static decision replaces authentication; it does not bypass authorization

canonical app host
  → resolve active app and current release metadata only
  → classify route
  → load current policy and current operator public gate
  → private route: validate session + evaluate viewer policy
  → public static route: evaluate explicit public-static policy
  → produce sealed StaticAccessContext
  → verify immutable release evidence
  → serve static bytes

reserved /_tinker/* on public app
  → deny before SDK, blob, realtime, or LLM dispatcher

The sealed context should be a sum type produced only by the gateway: private-viewer authorization or public-static authorization. Capability dispatchers continue to require the private viewer-bearing context. A boolean such as public=true or authorized=true is forbidden.

Candidate verification becomes posture-aware. A private deployment proves anonymous denial with zero release bytes. A public deployment proves the expected candidate bytes are anonymously reachable through the gateway while every reserved capability route remains denied.

  • The global identity is the source of viewer identity; browser query parameters never select an email or app.
  • The server queries only current active apps whose owner/email/domain policy matches that identity, plus public apps explicitly configured for catalog listing.
  • The response contains slug, active description, bounded tags, public/private badge, and stable URL—never denied app metadata.
  • Search and tag filtering operate only over the already-authorized server-rendered list.
  • Opening a private card still uses the normal app-bound handoff and rechecks current policy before any release byte is served.

Recommended tag contract: zero to eight immutable active-deployment tags, each 1–24 lowercase ASCII characters using letters, numbers, and internal hyphens. Tags are presentation metadata, never policy or capability selectors.

Basic local analytics

Answer only: did people visit, how often, and when?

Metrics

  • Visitors: approximate distinct browsers in the selected period.
  • Page views: successful HTML document responses.
  • Last activity: latest counted document response.
  • Daily series: visitor and page-view totals for the last 30 days.

Explicit omissions

  • No clicks or custom app events in the first slice.
  • No asset/API/WebSocket request counts.
  • No paths, queries, referrers, IPs, email addresses, names, user agents, or device fingerprints.
  • No claim to bot filtering or cross-device identity.

A successful top-level HTML GET or validated SPA fallback counts as a page view. Assets, ranges, source maps, reserved routes, health checks, deployment probes, errors, and non-document requests do not. Analytics failure never blocks an otherwise valid app response.

Analytics identity and ownership

Count browsers locally without building a tracking profile

  • The gateway issues a random, host-only, Secure, HttpOnly, SameSite=Lax analytics cookie. It is app-specific and has a 30-day maximum lifetime.
  • The database stores only an app-scoped keyed digest of that random value, never the cookie, IP, viewer session, email, or global identity.
  • A missing or blocked cookie still increments the page view but cannot contribute a reliable returning-visitor identity.
  • Daily aggregates and visitor markers remain in the existing control SQLite database and are retained for at most 30 days.
  • The app owner and operator may read aggregates. Viewers, app JavaScript, SDK calls, deployment agents, and unrelated deployers cannot.
  • Hard app deletion removes its aggregates and visitor markers. Analytics state never survives as an independent app record.

“Visitors” is deliberately approximate: one browser can represent multiple people, one person can use multiple browsers, and bots may be included. The UI must label the metric accordingly.

Deny-path charter first

Public static access must not become anonymous platform authority

Public publishing

  • Operator gate off, missing, stale, or unavailable denies anonymous bytes.
  • Private, unknown, suspended, deleting, failed, or corrupt apps deny anonymous bytes.
  • Public mode with KV, collections, blobs, realtime, LLM, or a future capability enabled cannot activate.
  • Every /_tinker/* route on a public app denies before a capability repository or provider is touched.
  • Public-to-private and global disable affect the next request and invalidate public cache behavior.
  • Wrong-host and cross-app requests never reuse another app's public decision.

Catalog and analytics

  • Anonymous catalog requests and denied viewer identities receive no private app metadata.
  • Policy revocation removes the card on the next catalog read.
  • App A owner cannot read App B analytics; deployment-agent and app SDK credentials cannot read any analytics.
  • Malformed dates, ranges, app slugs, tags, cookies, and digests fail within fixed bounds.
  • Analytics write failure does not alter authorization, static response bytes, or app availability.
  • Logs and database inspection prove no raw cookie, session, identity, IP, URL, referrer, or content retention.

Acceptance criteria

  • An operator can enable or disable permission for public apps without adding a listener, provider, daemon, or proxy.
  • A deployer can deliberately promote an owned, capability-free static app to public and receives a working anonymous URL only after posture-aware gateway verification.
  • An anonymous visitor can fetch public HTML/assets and cannot invoke any Tinkercloud SDK, blob, realtime, identity, login, or LLM route.
  • Disabling public access or returning the app to private denies the next anonymous request while normal private owner access remains possible.
  • A verified viewer sees a searchable catalog containing only current authorized private apps and explicitly catalog-listed public apps.
  • An owner sees approximate visitors, page views, last activity, and a 30-day daily series; repeated pages from one cookie count as one visitor and multiple views.
  • Analytics remains entirely local, bounded, deletable with the app, and non-blocking on failure.
  • Two-app/two-owner, anonymous, revoked, malformed, database-failure, restart, activation-failure, and public/private transition matrices pass on a real listener and clean VPS.

Rollout phases

  1. L0 — Governance and contracts. Amend PRD D3/FR-POLICY-006 as an explicit post-V1 decision, add the public-static threat model and ADR, define analytics privacy/retention, and update the manifest/API/test contracts before code.
  2. L1 — Basic local analytics on private apps. Count successful document responses, add bounded storage and owner dashboard summaries, verify privacy and non-blocking failure.
  3. L2 — Team catalog and tags. Replace the no-dashboard-role dead end with a policy-filtered viewer catalog; add active-manifest tags and local search.
  4. L3 — Operator-gated public static pilot. Implement public policy, sealed static context, capability-free activation, public/private transitions, dual deployment probes, and default noindex.
  5. L4 — Marketing evidence. Publish first-party example apps deliberately, opt selected examples into indexing, measure local visits, and run the full clean-VPS public/private matrix before making public mode generally available.

  • Refresh marked specialized-skill copies and run drift checks after every workflow change.

Open questions with recommended defaults

  • Should public apps ever use Tinkercloud capabilities? No. Public static only for the first release; revisit through a separate anonymous-capability concept with abuse budgets.
  • What does “users” mean in analytics? Label the value “approximate visitors” and derive it only from an app-host random cookie.
  • Should custom events count actions? No initially. Page views and visitors establish whether the app is used without adding an instrumentation SDK.
  • Should public apps be indexed? No by default. Require explicit per-app opt-in while the operator public gate is active.
  • Should every public app appear in the team catalog? Yes for signed-in team viewers by default; a future public showcase is a separate product surface.
  • Should analytics be on by default? Yes, local-only with 30-day retention and one global operator disable switch; never load third-party code.

Do or don't

Build the staged reach loop; do not build a general public app runtime

Do: Build analytics, catalog discovery, and operator-gated public static delivery as separate vertical slices. The impact is high: public examples create a marketing surface, the catalog strengthens everyday team use, and local analytics closes the learning loop. Each slice reuses the existing gateway, immutable releases, SQLite, native UI, and agent workflows.

Don't: add anonymous platform capabilities or user-authored server code. That would turn a controlled static-publishing feature into a public compute, storage, abuse, and spend platform. It has much higher complexity and permanently expands the trusted surface without being necessary for the marketing opportunity.

Concept decision: pursue public reach and simple local insights after the governance update; retain the fixed capability and single-gateway model.

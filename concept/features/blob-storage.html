Rank 5 · Planned V1 feature

Small app attachments without a storage project.

Let private static apps upload and retrieve bounded files through the same typed, app-scoped SDK they already use for JSON state.

Private local bytes; gateway-derived authority.

Reason and value

Files are a common primitive, not a backend runtime

Review tools, staff forms, image boards, exports, and document workflows quickly outgrow JSON KV. Requiring each tiny app to operate S3, signed URLs, CORS, and credentials would recreate the platform ceremony TinyHost exists to remove.

A constrained local capability serves the first useful apps while keeping one VPS, one gateway, one SQLite catalog, and one private data directory.

Impact4 / 5
Complexity3 / 5
Yield4 / 5

V1 scope

  • Opt-in features.blobs capability.
  • SDK upload, get, bounded list, and delete.
  • One app-shared namespace, matching V1 KV authority.
  • Opaque server-issued IDs and display-only filenames.
  • Private local bytes with SQLite readiness and quota state.
  • 25 MB per blob, 1,000 blobs, and 250 MB per app by default.
  • Attachment-only authenticated downloads with no sniffing.

Non-goals

  • No public or signed object URLs.
  • No filesystem paths, directories, or user-selected keys.
  • No resumable/multipart upload, replace, versioning, or search.
  • No thumbnails, transformations, or inline media-hosting promise.
  • No per-viewer blob ACLs in V1.
  • No FUSE/rclone/s3fs/Mountpoint or standalone MinIO service.
  • No remote durability, replication, or backup claim.

User flow

One typed capability

const stored = await tiny.blobs.upload(file);
const bytes = await tiny.blobs.get(stored.id);
const page = await tiny.blobs.list({ limit: 100 });
await tiny.blobs.delete(stored.id);

The app discovers the capability first. TinyHost derives the app and viewer from the current host session, checks current policy and limits, and never gives browser code a storage credential or app selector.

Implementation sketch

SQLite is the catalog; storage holds opaque bytes

authorized request
  → server-issued app + blob IDs
  → SQLite state=staging
  → bounded stream into unreachable local storage
  → close/sync and verify exact size/hash
  → SQLite state=ready
  → gateway-authorized attachment download

Only ready rows are listable or readable. Interrupted staging, deleting rows, or metadata/storage disagreement remain unavailable and are reconciled from server-derived IDs.

Capability contract · Storage ADR

Storage research

Use an object seam, not a mounted object store

Mountpoint, rclone, and s3fs can present S3 as files, but add a mount/daemon lifecycle and weaker rename, locking, cache, and coordination semantics. Go CDK offers a credible portable local/S3 blob API. V1 will spike that library against a small native adapter before accepting a dependency, while keeping the public contract independent of either choice.

Open questions

  • Does Go CDK fileblob earn its dependency cost over a narrow native local adapter under TinyHost failure injection?
  • Which bounded filename and content-type normalization gives useful display metadata without implying safe inline rendering?
  • What upload rate and concurrency defaults fit the smallest supported VPS while leaving deployment and revocation responsive?
  • Which gallery app best proves attachments without adding a broad media-management product?

Do or don’t

Include the constrained primitive in V1

Do: File attachments materially expand the tiny apps people can build, and the existing gateway, streaming, quota, and recovery foundations keep the slice bounded.

Don’t: Do not turn V1 into an S3 deployment, filesystem product, public asset host, backup system, or media pipeline.

Decision basis: impact 4/5, complexity 3/5, yield 4/5. The scope is useful only if partial writes and cross-app access remain release-blocking failures.

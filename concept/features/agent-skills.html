Teach agents the whole Tinkercloud contract.

Versioned skills turn SDK, manifest, capability, deployment, and denial-verification knowledge into a reliable app-building workflow.

An agent cannot call an app complete when protection has not been independently verified.

Reason and value

Documentation becomes an executable development interface

Non-technical deployers depend on coding agents making correct choices without rediscovering the platform. Skills make safe SDK use, capability discovery, access policy, deployment, and verification the default.

Scope

  • Generic canonical source first, then one standalone deployer lifecycle skill and one operator skill.
  • SDK, manifest, capability, security, and troubleshooting references.
  • Deterministic build and protection-verification scripts.
  • CI checks against real contracts and examples.
  • Versioning with compatible Tinkercloud releases.

Non-goals

  • No giant monolithic prompt.
  • No prose-only security verification.
  • No skill-owned secrets or deployer credentials.
  • No unchecked drift in intentionally copied shared sections.

Implementation sketch

Generic first, standalone copies, executable checks

tinkercloud-platform
  → canonical shared vocabulary + security rules
  → copy marked relevant sections into each specialization
  → CI generator/check rejects drift

tinkercloud-deployer
  → understand or inspect the app
  → choose SDK capabilities
  → propose access policy
  → build + validate manifest
  → deploy immutable release
  → verify anonymous denial
  → verify authenticated behavior

tinkercloud-operator
  → install, diagnose, grant, update, recover

Do or don’t

Build alongside SDK and CLI behavior

Do: Skills are essential to the staff usability model and cheap to keep correct when examples are contract-tested.

Don’t: Do not postpone them until after APIs stabilize; designing for agent comprehension will improve the APIs themselves.

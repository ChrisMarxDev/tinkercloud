One domain. One browser identity. Isolated app sessions.

An operator supplies one root domain. admin.<domain> is both the dashboard and the only browser identity broker; each deployed app lives at <slug>.<domain> with its own host-only child session.

Authenticate a viewer once without turning sibling apps, dashboard access, or CLI authority into the same permission.

Reason and value

Make the browser model understandable without weakening isolation

The earlier concepts distinguished a platform host from app hosts and retained a separate dashboard browser session. That creates an avoidable second browser login model. A single exact admin origin gives operators, deployers, and viewers one place to verify an email, while the gateway still decides dashboard role and app access independently at use time.

The operator configures *.<domain> once. DNS wildcard routing and TLS coverage are separate: a wildcard DNS record does not supply a certificate. TinyHost may issue certificates on demand for each exact admin/app host; a wildcard certificate is optional.

Scope

  • Exactly one operator-provided root domain and a wildcard app namespace.
  • admin.<domain> is the sole browser OTP, identity switch, global logout, and dashboard origin.
  • One opaque, host-only platform identity cookie on admin; it is never sent to an app host.
  • Server-created, app-bound, one-time handoffs issue opaque host-only child sessions on allowed app hosts.
  • Dashboard role authorization and each app’s viewer allowlist are distinct current-policy checks.
  • Safe relative path plus query survives a broker round trip; URL fragments are client-side and are not guaranteed to survive.

Non-goals

  • No parent-domain cookie, shared app cookie, JWT, browser storage token, or client-selected app identity.
  • No compatibility layer for the old separate dashboard browser login/session model; remove and migrate it deliberately.
  • No authority transfer based on matching email: viewer identity alone grants neither operator nor deployer role, nor app access.
  • No use of CLI bearer tokens as browser credentials or of browser cookies as API bearers.
  • No promise to preserve fragments across authentication or handoff navigation.

Authority split

  • Browser identity: which verified email identity is present at admin.
  • Dashboard authorization: whether that identity currently has an operator or deployer dashboard role.
  • App authorization: whether that identity is allowed by the resolved app’s current policy.
  • CLI authorization: a separate scoped bearer token with its own issuance, expiry, and revocation.

Implementation sketch

Identity crosses origins only through a narrow server-owned handoff

viewer opens https://reports.<domain>/quarterly?tab=open
  → gateway derives app from canonical host
  → no child session: store app + safe path/query + one-time state
  → redirect to exact https://admin.<domain>/identity/…
  → admin validates or creates one browser identity by OTP
  → gateway checks current reports allowlist
  → exact app callback consumes state and rechecks policy
  → set host-only reports child session
  → redirect to /quarterly?tab=open

The broker never trusts an app ID, callback origin, identity, role, or return URL supplied by browser code. The app is resolved from the exact host; the callback target and handoff state are stored server-side. A child session is valid only for its resolved app and remains subject to current policy on every protected request and WebSocket upgrade.

Logout: app-local logout revokes only the current app child session. Global TinyHost logout at admin revokes the platform identity and every derived child session after the revocation transaction commits. It does not revoke CLI tokens. An identity switch similarly invalidates the previous identity’s child sessions.

Security and delivery risks

Siblings are same-site, not the same origin

  • Browser same-site behavior across sibling subdomains is not an authorization boundary. Every state-changing route requires exact HTTPS Origin matching its own host and its own CSRF defence.
  • Use __Host- cookies: Secure, Path=/, no Domain, and HttpOnly. Validate that an app host cannot receive or overwrite an admin cookie.
  • CORS is deny-by-default: no credentialed cross-origin browser API between admin and apps; handoff navigation is not a CORS permission.
  • Canonical host parsing, reserved-label rejection, and exact redirect construction must precede app content lookup. Unknown or malformed hosts return no app bytes.
  • Wildcard DNS is not TLS evidence. Setup and activation need trusted certificate proof for each exact served host, including renewal and failure handling.

Acceptance and deny-path charter

  • Only admin.<domain> issues browser identity; app-host OTP routes and the old dashboard browser-session path are absent or deny without mutation.
  • The admin identity cookie is absent from every app request; App A’s child session cannot authenticate App B, admin, or the CLI.
  • An identity with dashboard role but no app allowlist entry is denied that app; an allowlisted viewer with no dashboard role is denied dashboard data.
  • Guessed, expired, replayed, cross-app, state-mismatched, or policy-revoked handoffs issue no child session and serve no app bytes.
  • Exact Origin/CSRF, CORS, reserved-label, canonical-host, and DNS/TLS mismatch tests deny before protected dispatch.
  • Path and query return exactly after a successful handoff; fragments are explicitly untested/non-guaranteed.
  • App logout leaves other app sessions and admin identity intact; global logout/switch invalidates all children while leaving CLI tokens unaffected.

Implementation gate

The replacement has no compatibility browser-session path. It is not complete until local and live evidence proves exact-host certificate coverage, handoff replay denial, role/policy separation, app-local and global logout scope, and safe path-plus-query preservation.

Do or don’t

Do the replacement before adding another browser feature

Do: Replace the duplicate dashboard browser identity model with the exact admin broker and preserve app isolation with host-only children. It simplifies human understanding while strengthening credential separation.

Don’t: Do not bridge old and new browser sessions in the name of compatibility. That would leave two issuance paths and make global logout, revocation, and audit semantics ambiguous.

Locked architecture. Completion requires replacement-code, migration, and security verification evidence.

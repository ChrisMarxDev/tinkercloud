Inspect an app’s data from the CLI without exposing its database.

Give an authenticated deployer bounded API and CLI access to the KV entries and JSON documents of an app they own. Tinkercloud still derives the immutable app identity, keeps SQLite private, and applies current authorization on every request.

Owner-scoped data operations, not remote SQL.

Reason and value

Make support and recovery possible without VPS access

Today a deployer can create, deploy, configure, and observe an app, but cannot safely inspect the state created through Tinkercloud’s SDK. Bounded data access makes it practical to diagnose a broken poll, repair one malformed document, confirm an import, or automate a controlled export. It uses the same app-local data model as the SDK and does not create a second database authority.

Scope

  • Authenticated deployer access to an app the deployer owns.
  • Bounded KV list/get and collection/document list/get operations.
  • Stable JSON HTTP responses and deterministic CLI --json output.
  • Cursor pagination, existing size limits, and explicit versions.
  • Separate data:read and data:write token scopes.
  • Later single-record mutations with optimistic concurrency.

Non-goals

  • No SQL console, query language, joins, filters, schemas, or migrations.
  • No SQLite file download, database path, connection string, or second listener.
  • No viewer impersonation or client-selected immutable app ID.
  • No unbounded dump, bulk delete, or server-side backup product.
  • No automatic data access for operators or deployment agents.
  • No realtime CLI tail or durable change-history promise.

Deployer experience

The saved login is enough; ask only for the target and operation

tinker data kv list my-app --prefix settings/
tinker data kv get my-app settings/theme

tinker data collections list my-app
tinker data documents list my-app tasks --limit 50
tinker data documents get my-app tasks doc_abcdefghijklmnopqrstuv

# Stable machine-readable output for every command
tinker data documents list my-app tasks --json

The CLI reuses its saved Tinkercloud server and deployer login. It does not create a local database configuration, request a database credential, or ask for information Tinkercloud can derive. Human output is readable; --json preserves the versioned API envelope for scripts.

Proposed control API

App slug in; server-derived data scope out

GET /api/v1/apps/{slug}/data/kv?prefix=&cursor=&limit=
GET /api/v1/apps/{slug}/data/kv/{key}

GET /api/v1/apps/{slug}/data/collections?cursor=&limit=
GET /api/v1/apps/{slug}/data/collections/{collection}/documents?cursor=&limit=
GET /api/v1/apps/{slug}/data/collections/{collection}/documents/{id}

The public slug is an owned control-plane resource identifier, not a database selector. After authenticating the deployer and checking data:read, the server verifies ownership, resolves the immutable app ID, and produces a typed app-data authorization context. Only that context may reach the existing KV and collection services.

Do not call the protected app dispatcher with a synthetic viewer session or an authorized=true flag. Refactor the shared data services to accept a narrow context containing server-derived app, authenticated owner subject. The app gateway and control gateway may each produce that context only after their own authentication and authorization succeeds.

Deny-path charter first

  • Anonymous requests, browser identity cookies, and app viewer cookies cannot use the bearer-token data API.
  • A deployer cannot read another deployer’s app, even with a valid token and guessed slug.
  • Missing, expired, revoked, suspended, wrong-app, or wrong-scope credentials fail before opening an app database.
  • Malformed slugs, keys, collections, document IDs, cursors, limits, and encoded path separators fail closed.
  • Responses and errors never reveal another app’s bytes, a filesystem path, SQL, schema details, or secrets from logs.
  • Oversized pages, quota exhaustion, unavailable/locked databases, and cancellation return stable safe errors.
  • Future writes reject stale versions and partial mutations; an audit failure must not leave an unaudited write committed.

Trust and ownership

  • Owner: the app remains owned by its deployer; app data remains isolated in its app-local SQLite file.
  • Trust boundary: the platform gateway authenticates the deployer and resolves ownership before data access.
  • Credential: a fresh interactive CLI login receives data:read/data:write; deployment-agent tokens receive no data scope by default.
  • Revocation: deployer suspension, app deletion, or token revocation applies on the next request.
  • Observability: record actor, app, operation, result, and request ID—never values or document bodies.

Implementation evidence

  1. L1 — Read one document. Added the contract, ADR, data:read authorization, typed app-data context, one document-get endpoint, CLI command, audit metadata, and cross-app negative tests.
  2. L2 — Bounded browsing. Added KV list/get, active collection-name listing, paged document listing, stable JSON output, and local two-owner HTTP integration evidence. Live-VPS acceptance with two deployers and two apps remains the release exit gate.
  3. L3 — Deliberate mutation. Added data:write, individual KV set/delete and document create/update/delete. Require expected versions for update/delete, accept JSON from a file or stdin, and confirm destructive actions.
  4. L4 — Evidence-led portability. Consider a paged client-side JSONL export/import only after real demand. Never turn it into a raw database download or V1 backup claim.

Implemented decisions and remaining evidence

  • Interactive owner logins gain data:read and data:write only when freshly issued; machine/deployment-agent tokens must request each scope explicitly and remain app-scoped.
  • Reads for an owned suspended app support diagnosis, but permit writes only while active; deny all access once deletion begins.
  • Writes record metadata-only intent/digest and a successful outcome without storing values; interrupted outcomes reconcile only from provable current state.
  • The two-owner/two-app live VPS denial matrix remains the release evidence gate.

Do or don’t

Build a narrow data administration API; do not expose SQLite

Do: Ship the read-only slice first. It has high operational value at moderate complexity because it composes the existing ownership, bearer-token, KV, collection, pagination, and per-app database boundaries.

Don’t: Add raw SQL or database downloads. They would bypass capability limits, couple the public interface to internal schema, increase exfiltration and corruption risk, and contradict the single private data authority for little additional user value.

Implemented locally as an M4 capability. The two-owner live VPS denial matrix remains release evidence.

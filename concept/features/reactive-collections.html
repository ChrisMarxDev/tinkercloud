Feature rankingProduct concept

Implemented M4 app-platform slice

Save a document once. Keep every open app current.

Give deployers Shopify Quick-style collection CRUD and subscriptions without introducing a remote database, a second service, or durable WebSocket history.

SQLite owns current state; sockets announce committed change; the SDK reconciles after every gap.

Reason and value

Make the correct realtime pattern the easiest pattern

TinyHost already combined durable versioned KV with ephemeral app-scoped WebSocket hints, but app authors had to compose reads, prefixes, reconnect recovery, and rendering themselves. The implemented collection API makes polls, checklists, comments, dashboards, and shared tools reliable by default while preserving the existing single-process architecture.

Scope

  • App-scoped named collections containing bounded JSON documents.
  • Create, get, update, delete, and bounded list operations.
  • Server-issued document IDs and explicit document versions.
  • Snapshot subscriptions with optional create/update/delete callbacks.
  • Automatic initial load, reconnect reconciliation, and visibility recovery.
  • Raw KV and custom live channels remain available as lower-level primitives.

Non-goals

  • No browser SQL, schemas, migrations, joins, or arbitrary queries.
  • No direct SQLite, Turso, or database credential in app code.
  • No durable event replay or ordered message-stream promise.
  • No second database service, remote authority, or multi-node design.
  • No client-selected app or viewer identity.

Creator experience

Quick-like intent, TinyHost recovery semantics

const tasks = tiny.db.collection("tasks");

await tasks.create({ title: "Ship it", done: false });

const stop = tasks.subscribe({
  onSnapshot: (snapshot) => render(snapshot.documents),
  onCreate: (document) => animateIn(document),
  onDelete: (id) => animateOut(id),
  onStatus: (status) => showSyncStatus(status),
});

The snapshot is authoritative. Per-change callbacks are conveniences derived by comparing reconciled snapshots and are never presented as a durable event log.

Implemented shape

Commit first, notify second, reconcile always

authorized collection mutation
  → one SQLite transaction updates app-scoped document + collection revision
  → commit succeeds
  → in-process change sink publishes bounded collection.changed hint
  → app-scoped WebSocket hub fans out to matching subscribers
  → SDK reloads or incrementally verifies current collection state
  → reconnect or tab resume forces a fresh snapshot

Each server-derived app owns a private apps/{immutable-app-id}/data.db. Its app_documents rows are keyed by collection and document ID, with a monotonic per-collection revision updated in the same transaction. The control database contains no shared app-data table and request composition has no legacy KV fallback. Subscribe before loading the initial snapshot; queue hints received during that load; repeat reconciliation until no newer hint remains.

The current service-level change sink already runs after successful repository mutation and retains the server-derived authorization context. Keep that explicit seam. A generic SQLite update hook fires per connection with weaker commit semantics, while a durable CDC table adds cursor, retention, and cleanup work that this single-process design does not need.

Deny-path charter

  • Anonymous, cross-app, revoked, and capability-disabled reads, writes, and subscriptions fail before document access.
  • Malformed names, IDs, JSON, versions, cursors, and oversized documents are rejected.
  • Failed or rolled-back transactions emit no hint.
  • Slow consumers close without blocking writers or other viewers.
  • Reconnect never treats an event gap as an empty collection.

Do or don’t

Build the behavior; do not replace SQLite to obtain it

Do: Add a small collection model and make synchronization an SDK responsibility over committed SQLite state and the existing app-scoped WebSocket hub.

Don’t: Move to Turso or another database merely for a change listener. Reconsider CDC or replication only if TinyHost later gains multiple writers, multiple server processes, or remote replicas.

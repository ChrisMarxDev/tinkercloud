Rank 7 · Planned feature

Hetzner-first native deployment

Turn a clean, dedicated Hetzner VPS into a working TinyHost server with a thin install script and one signed server binary.

The script downloads; the binary owns setup, validation, service installation, diagnostics, update, and recovery.

Reason and value

Operational ease is part of the product

A technically capable operator should not need to assemble a reverse proxy, container stack, certificate service, database, or migration runner. One supported clean-host shape makes installation predictable, diagnosis actionable, and AI-guided operation reliable.

Impact5 / 5
Complexity4 / 5

Scope

  • Clean Hetzner Cloud Linux VPS with systemd.
  • Signed tinyhost server binary and systemd unit.
  • Interactive, resumable initialization and DNS/email/TLS checks.
  • Dedicated unprivileged service user and private data directory.
  • Root-only operator recovery independent of email.
  • Signed self-update with health-gated automatic rollback.
  • Separate small tiny client distribution.

Non-goals

  • No Docker, Kubernetes, external reverse proxy, or multi-host setup.
  • No unattended silent updates in V1.
  • No operator backup or disaster-recovery system.
  • No promise of every Linux distribution on day one.
  • No remote recovery endpoint that bypasses normal authentication.

Implementation sketch

Small script, authoritative binary

install.sh:
  detect architecture
  download tinyhost
  verify checksum and signature
  exec "tinyhost install-service"

tinyhost init:
  validate clean host + DNS
  create user, config, secrets, data directory
  initialize SQLite
  test Resend
  provision TLS
  start systemd service
  run health + anonymous-denial probes
  print dashboard and recovery commands

Open questions

  • Which exact Linux image and architectures form the first tested support matrix?
  • What signing mechanism and trust-root rotation ceremony are simplest for operators?
  • How should migrations declare whether automatic binary rollback is safe or requires a forward recovery?
  • Should an opt-in systemd timer for updates ship in V1 or immediately after?

Do or don’t

Build one excellent host path

Do: A narrow Hetzner-first path directly serves the initial operator, supports deterministic testing, and preserves the single-server-binary promise.

Don’t: Do not generalize into containers and universal Linux packaging before the native clean-host loop is dependable. The self-contained binary keeps those later options feasible.

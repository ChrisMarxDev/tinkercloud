Actor flow · Deployer · July 2026

From a built folder to a protected useful app.

The complete journey covers authorization, signed client installation, deploy-first onboarding, persistent login, generated manifest, verified activation, daily management, account switching, logout, and permanent app deletion.

The deployer runs tiny deploy .. TinyHost asks only for a necessary decision it cannot safely infer.

Reason and value

Deployment is the task; configuration is the receipt

A deployer should not learn VPS layout, TLS, archive security, auth middleware, config schemas, or credential-store commands. They bring an already built static app and the platform performs the protected release loop.

Impact5 / 5
Complexity3 / 5
Yield5 / 5

Scope

  • Operator-authorized deployer email.
  • Signed macOS/Linux tiny client.
  • Useful static project; existing build output is reused, while missing output produces one exact project-owned build action.
  • Verified default platform and persistent scoped bearer.
  • Generated manifest and owner-only secure default.
  • Immutable deployment, protection proof, dashboard management, and deletion.

Non-goals

  • No VPS, DNS, Resend, TLS, or server config knowledge.
  • No automatic execution of project build scripts.
  • No project-local deployer credential.
  • No public app or implicit viewer-access broadening.
  • No deployer-selected release rollback.
  • No required hand-authored tiny.yaml.

Phase A · Authorization and local project

Start with a real app, not platform ceremony

#Deployer actionSystem or external action Information requestedDerived or defaultedNecessity gate
1 Receive the TinyHost platform URL from the operator. The operator has already placed the deployer email in the global active allowlist. No invitation account, password, team, or organization setup. The existing email inbox is assumed. Only the platform address and prior authorization are needed.
2 Install the signed tiny client as the normal OS account, without sudo. The installer selects the local OS/architecture and verifies the release signature before writing to the per-user executable location. An alternate signed release source only when intentionally overriding the trusted default. OS, architecture, and install path. The deployer should not choose server artifacts or system paths.
3 Open a useful static application project. The existing framework/toolchain remains responsible for source and dependencies. No TinyHost project template is required. The current directory is the project root. TinyHost hosts built static output; it does not own the app’s build system.
4 Run tiny deploy . from the project root. The CLI begins local, platform, authentication, manifest, and deployment preflight as one resumable flow. None yet. Project path defaults to the current directory. A separate build or init ceremony is not required when valid output already exists.
5 If no valid built output exists, run the exact project-owned build action Tiny identifies, then rerun tiny deploy .. TinyHost never executes the build; with existing output it skips this branch entirely. No build-command prompt. Existing build scripts/toolchain remain authoritative. Building is necessary only when output is absent; arbitrary local script execution remains outside TinyHost.

Phase B · Platform and identity wizard

Ask once, verify, and reuse

#Deployer actionSystem action Information requestedDerived or defaultedNecessity gate
6 If no default exists, enter the HTTPS platform URL received from the operator. Tiny normalizes it, follows no redirect, proves API compatibility, and saves only the verified non-secret URL. One platform URL, once. Later human commands reuse it. An explicit --server override is invocation-only. The CLI cannot discover which independent TinyHost the deployer intends to use.
7 If a saved bearer exists, provide no input. Tiny calls version and authenticated whoami; a valid bearer confirms the deployer and continues silently. None. Server and identity come from protected saved state and server proof. Repeated login is unnecessary while current authorization remains valid.
8 If no valid bearer exists, enter the authorized deployer email. The platform sends a generic OTP response that does not reveal allowlist membership. Email only when authentication is actually required. The verified default server is reused. Identity cannot be guessed; transport/5xx/ambiguous failures must not trigger OTP automatically.
9 Enter the emailed one-time code. The server verifies code, expiry, attempts, active deployer status, and issues a server-bound scoped CLI bearer. One OTP. No password, magic-link requirement, or project token. Possession of the authorized mailbox is the V1 remote authentication proof.
10 Provide no storage choice or password. Tiny confirms the new bearer with whoami, then atomically stores it in the protected per-user Tiny credential file. None. OS config path, hashed server filename, directory/file modes, and atomic replacement. Credential mechanics are not a product decision. Failure preserves any previous valid credential.

Phase C · Project discovery and manifest receipt

Derive safe state; ask only about ambiguity

#Deployer actionSystem action Information requestedDerived or defaultedNecessity gate
11 If a valid tiny.yaml exists, provide no input; otherwise provide no manifest. Tiny validates and reuses an existing manifest without rewriting. When absent, it inspects only the non-symlinked project and conventional static-output candidates. None when explicit valid manifest state or exactly one safe output exists. Existing reviewed manifest wins; otherwise slug comes from the directory and output from unambiguous evidence. Known explicit state and filesystem facts should not be re-entered.
12 If multiple valid outputs exist, select the intended directory. If none exists, stop and build rather than choosing an arbitrary folder. Tiny validates the selected path remains beneath the project and contains a deployable entry document. Output directory only when discovery is ambiguous. No framework selection or build command. Uploading the wrong directory is unsafe; choosing among ambiguous evidence is necessary.
13 If the derived slug is invalid or generically unavailable, enter a replacement app name. Tiny normalizes and checks the stable slug against platform rules/ownership; an existing same-owner app is reused automatically. App name only when the directory default cannot work. Valid directory name or existing same-owner app otherwise. A stable hostname needs a valid slug; asking every deployer is unnecessary.
14 Provide no standalone capability answer. Tiny reuses explicit manifest capabilities or defaults to none. Detected SDK usage may produce a warning/evidence in review, never authority. Capabilities are entered only through deliberate “Edit” intent. No capability by default; never enable surface from unproven build inspection. An answer must express deployer intent; detection alone cannot prove required authority.
15 Review one deployment screen: server, slug, output, owner-only/current policy, immutable description, capabilities, fallback, and limits. Choose “Edit” only for deliberate customization. Tiny displays slug, output, owner-only access, capabilities, fallback, server, and limits. No intermediate confirmation; optional values only after choosing “Edit.” Owner-only private access, empty description, no fallback, and explicit-manifest capabilities or none. Optional product metadata must not become mandatory questions. Access broadening is explicit.
16 Choose one final action. When access broadens, its label names the consequence, for example “Deploy and grant access to 3 addresses.” Tiny normalizes viewer rules, binds the candidate private policy, and begins deployment. One explicit final action; broadening is part of that same clearly named action. The deployer owner remains an implicit viewer. Authorization broadening must never be inferred from convenience.
17 Provide no separate manifest confirmation. After the single final action, Tiny atomically writes a missing strict deterministic tiny.yaml without overwriting an existing file. No YAML syntax, schema version, config path, or “accept manifest?” question. Manifest location is the project root and records the reviewed choices. The file is a consequence/receipt of the confirmed deploy, not another decision.

Phase D · Immutable protected deployment

Success means the app works and anonymous access fails

#Deployer actionSystem action Information requestedDerived or defaultedNecessity gate
18 After the one final action in step 16, provide no more input on the happy path. Tiny validates manifest, credential, paths, symlinks, limits, policy, and server compatibility before creating bytes. No second deploy approval; no app ID, owner ID, archive path, or hostname. App identity/ownership and stable URL are server-derived. One deployment intent must not become review + manifest + deploy confirmations.
19 Wait while the CLI archives and uploads. Tiny creates a private deterministic temporary archive, streams it with a fresh idempotency key, and always removes the temporary file. None. Archive format, temporary path, idempotency key, and upload endpoint. Transport mechanics are not questions.
20 Continue waiting through validation. The server quota-checks, inspects the hostile archive, extracts into unreachable staging, hashes files, seals an immutable release, and persists candidate evidence. None. Release ID, storage path, content hashes, and state transitions. Security validation must be automatic and fail closed.
21 Continue waiting through first-host readiness. The server creates/checks private policy, retries only bounded certificate readiness for the exact app host, then atomically activates. None. App hostname from slug plus server suffix; certificate operations from current host state. Certificate delay is not a reason to supply TLS data. On exhaustion, the prior active release remains; a first app stays inactive and receives one actionable retry.
22 Continue waiting through verification. Server and CLI independently probe platform health and exact anonymous denial for HTML/assets/reserved APIs without cookies or bearer. None. Probe URLs and expected denial envelope are server-derived. A private deployment is not successful until unauthorized bytes are proven unavailable. Failure preserves the prior release (or leaves a first deployment inactive); no rollback selector is offered.
23 Open or copy the returned stable protected URL. Tiny reports URL, deployment ID, immutable description, capabilities, and policy summary only after all gates pass. None. Stable URL and IDs come from the activation result. Never ask the deployer to construct or guess an app URL.

Phase E · Daily app management

Manage only owned apps through narrow controls

#Deployer actionSystem action Information requestedDerived or defaultedNecessity gate
24 Open the dashboard and enter the deployer email when desired; matching email text does not reuse a viewer credential. The platform creates a control session distinct from the CLI bearer and viewer sessions. OTP only when no valid browser control session exists. Platform and account can be reused or deliberately changed. Credential types remain separate even when one person uses them.
25 Search owned projects by slug/current description or filter by status. Local enhancement filters the server-authorized list; no hidden app becomes visible. Search/filter values only when used. Owned apps, descriptions, status, counts, and URLs are server-derived. Do not require app IDs or repeated server queries for local narrowing.
26 Use the active app’s direct-link icon to open it. The link targets only the stable gateway origin and normal viewer authorization still applies. None. URL from server-controlled slug and app suffix. Convenience must not expose raw release/storage URLs.
26A Continue as a viewer when the app opens. App URL → app-bound handoff → existing global viewer identity or OTP → current policy checks → isolated app-local session. Viewer email/OTP only when no current global viewer identity exists or an explicit account switch is requested. App and policy come from the host/server. Deployer/control authority grants no viewer access. Matching email may be allowed as owner, but the credential boundary never transfers.
27 Edit viewer email/domain access when needed and confirm broadening. TinyHost revision-checks and atomically replaces current private policy; removal affects the next request and closes matching live access. Only intended viewer rules and broadening confirmation. Owner rule, app ID, policy revision, sessions, and revocation targets. The deployer decides who may view; internal policy selectors are server-derived.
28 Create/revoke scoped deployment-agent tokens only when automation is needed. TinyHost shows a new secret once, stores only its hash, and enforces scope/expiry/ownership on every use. Choose the narrow deployment-only preset; raw scopes/expiry appear only behind “Edit,” and broader scope requires explicit confirmation. Bounded default expiry, token ID, random secret, owner, and server. A token is unnecessary for normal interactive deploys.
29 Read immutable deployment history and current description. The dashboard shows release metadata but no deployer rollback action. None. Current pointer and historical immutable records. Failed-candidate preservation exists; selecting an old release is deliberately outside V1.
30 Deploy a new build with tiny deploy .. Tiny reuses platform, credential, and manifest, then repeats validation/activation/protection proof. No confirmation when state is unchanged. Ask only for local ambiguity or explicit policy broadening. Known project/server/identity values are not re-asked. Repeat deploy should feel like one command, not onboarding again.

Phase F · Account control and permanent deletion

Make identity changes and destructive intent explicit

#Deployer actionSystem action Information requestedDerived or defaultedNecessity gate
31 Run tiny login --force to change deployer account. Tiny keeps the previous bearer until fresh OTP and whoami prove the new account, then atomically replaces it. New email and OTP. Server and credential path. Account switching is deliberate; ordinary login should not repeatedly prompt.
32 Run tiny logout to stop using the CLI account. The server revokes exactly the current CLI bearer; only confirmed revocation/already-unauthorized state permits local deletion. The default server remains. No token ID, server URL, or confirmation on the normal path. Exact bearer from authentication context and its local file. Logout must be real revocation, not just local cache deletion.
33 Choose “Delete app” only when the app and its data are disposable. The dashboard names the app and exact irreversible consequences. Type the exact confirmation delete:<slug>. App ID, owner, data/storage paths, sessions, tokens, live connections, and cleanup targets. Permanent deletion needs app-bound proof of intent; internal paths must never be entered.
34 Wait for deletion completion. TinyHost first fails the app closed, closes live connections, then permanently removes app-owned policy, deployments/releases, tokens, viewer sessions, KV, blobs, app audit, and server-derived bytes. None. All deletion targets are derived from the owned app. Success is impossible while cleanup remains uncertain.
35 Accept that the former slug is now unknown and reusable only through a new app creation. No tombstone, trash, restore action, or deployer rollback remains. None. Hard deletion is the playground model. Retention ceremony and false recovery promises are intentionally absent.

Implementation sketch

One command composes bounded existing contracts

tiny deploy .
→ discover project + verified default platform
→ reuse bearer or complete OTP
→ derive safe manifest defaults
→ ask only for ambiguity or explicit customization
→ write manifest receipt
→ validate + archive + upload
→ stage + seal + certificate readiness
→ atomic activation
→ anonymous-denial + health proof
→ stable protected URL

JSON/automation takes explicit server, credential, manifest, and output state and never prompts or creates missing prerequisites.

Open questions

  • What build evidence can safely propose KV/blob/realtime capabilities without enabling unused surface or missing minified SDK use?
  • Should the first-run review use one editable summary or a compact numbered menu while remaining accessible in basic terminals?
  • When a slug collision belongs to another deployer, what generic wording avoids resource enumeration while still giving a useful next action?

Do or don’t

Make deploy-first the canonical human path

Do: Reuse verified state, derive project facts, default to owner-only, and expose optional settings through one review/edit checkpoint.

Don’t: Do not run builds, infer access broadening, hide security probes, store credentials in projects, or ask the deployer to author internal IDs, URLs, archive paths, or YAML.

Decision basis: impact 5/5, complexity 3/5, yield 5/5. Every prompt must justify itself against Principle 17.

Product concept Deployer flow Principles PRD

Actor flow · Operator · July 2026

From no server to a tinker private cloud.

The complete human journey includes buying the VPS and domain, creating DNS and email-provider state, installing Tinkercloud, granting deployment authority, operating apps, updating, and recovering.

Ask only for a necessary value that Tinkercloud cannot discover or safely default. Generate config as a receipt.

Reason and value

One understandable host, one guided setup

The operator wants a working private-app platform, not a lesson in reverse proxies, SQLite, systemd, ACME, or config schemas. Tinkercloud owns those mechanics while leaving account ownership, DNS, SSH, firewall policy, and the VPS lifecycle with the operator.

Impact5 / 5
Complexity4 / 5
Yield5 / 5

Scope

  • Dedicated supported public Hetzner VPS.
  • Operator-owned domain, DNS, SSH, and firewall.
  • Resend sending-domain verification and API credential.
  • Signed install, resumable setup, TLS, and health proof.
  • Operator login and exact active-deployer allowlist.
  • Diagnostics, app intervention, signed update, and root recovery.

Non-goals

  • No Docker, reverse-proxy assembly, or database service.
  • No Tinkercloud ownership of SSH or provider firewall policy.
  • No DNS-provider or registrar credentials in V1.
  • No public-app mode or blanket VPN identity bypass.
  • No operator backup or total-VPS-loss recovery guarantee.
  • No hand-authored config required for the human path.

Phase A · External ownership

Acquire the things Tinkercloud cannot create

#Operator actionSystem or external action Information requestedDerived or defaultedNecessity gate
1 Use an existing domain or buy one from a registrar. The registrar establishes domain ownership and a DNS control plane. Tinkercloud asks for nothing yet. Registrar billing/contact data stays external. Existing email inboxes are assumed; Tinkercloud does not provision mailboxes. A controlled domain is necessary for stable HTTPS platform and app hosts.
2 Create a dedicated Hetzner VPS using the supported Ubuntu LTS image and x86-64 architecture. Hetzner allocates a public IPv4 address and, when selected, IPv6. Hetzner may ask region, billing, plan, and account data; Tinkercloud asks none of it. Provider, OS, and architecture are fixed by the V1 support contract. Use the documented smallest validated plan when published. A public supported host is necessary; provider-shopping questions do not belong in Tinkercloud setup.
3 Add an SSH public key during VPS creation and connect as root. SSH presents a host key; the operator verifies and records it before trusting the shell. SSH key selection and host-key trust are external operator decisions. Tinkercloud never creates or uploads the operator’s SSH credential. Root access is the installation and recovery authority.
4 Configure the cloud/host firewall. Permit public TCP 80/443 and deliberately scope TCP 22 to the operator’s needs. No application ports, database ports, or storage ports are requested. Tinkercloud’s only public listener is the gateway on 80/443. HTTP is required for ACME; HTTPS is required for the platform. SSH policy remains operator-owned.
5 Obtain the Tinkercloud installer and signed release from a trusted release source. The thin installer verifies checksum and signature before installing the binary. No release URL is asked when the installer has a trusted built-in source; an explicit source is an advanced override. Architecture is discovered from the host. Unsigned or unverifiable code must not become the trust root.

Phase B · Guided bootstrap

Run one resumable setup assistant

#Operator actionSystem or external action Information requestedDerived or defaultedNecessity gate
6 Run sudo tinkercloud setup. Tinkercloud checks root authority, exact OS/architecture, clock, disk, ports, public IPs, and resumable state before mutation. None. Host facts are discovered; unsupported or conflicting state produces one exact correction. Never ask a person to type information the server can inspect.
7 Enter the controlled root domain. Tinkercloud normalizes it and previews the resulting topology. One base domain, for example example.com. admin.example.com, <slug>.example.com, and access@example.com. Domain ownership cannot be discovered. Separate dashboard/app/sender questions are unnecessary.
8 Enter the initial operator email. Tinkercloud normalizes it and uses it as the control identity and persisted internal ACME contact. One existing inbox address. ACME contact defaults to the operator email. No separate question. The first operator identity and delivery target cannot be inferred safely.
9 Inspect the derived setup summary; choose “Edit” or “Cancel” only when needed. Tinkercloud displays derived values, then continues because tinkercloud setup already expresses installation intent. No generic confirmation. Optional edits are entered only after choosing “Edit.” All conventional values remain selected without individual prompts. A second “continue?” prompt adds no decision after an explicit setup command.
10 Create or reuse a Resend account and add the derived sending domain. Resend supplies domain-verification DNS records. Provider account/billing data remains external. The sending domain defaults to the controlled base domain. Collect provider records before visiting DNS so all records can be added together.
11 Create a narrowly scoped Resend API key and keep it in a protected local/root-readable source while DNS is pending. Resend creates the provider credential; Tinkercloud has not ingested it yet. No key value is entered into argv, config, or the paused assistant. The final root-owned destination and permissions are generated later. Creating the key now avoids a second provider visit and does not weaken its destination boundary.
12 Leave the assistant paused at one combined DNS checkpoint. Tinkercloud saves validated non-secret progress and prints its records beside the Resend-supplied records. None. One A * → VPS IPv4 wildcard record; matching AAAA only for discovered usable IPv6. DNS is external and eventually consistent; re-entering prior answers is unnecessary.
13 Add the Tinkercloud host records and Resend’s exact verification records in one DNS-provider session. Public DNS propagates; Resend verifies domain ownership. Only record names/values from Tinkercloud and Resend. No zone-file/config authoring and no Tinkercloud DNS-provider credential. One combined external visit preserves both ownership boundaries with less ceremony.
14 After DNS and Resend verification, resume tinkercloud setup and provide the protected credential source. The assistant verifies DNS/provider state and copies the key into the root-owned credential boundary. Either a root-readable key-file path or the secret through a no-echo prompt. The credential destination, permissions, provider name, and config reference are generated. The secret itself is necessary; asking for a YAML/env file layout is not.

Phase C · Automatic installation and proof

Tinkercloud performs the infrastructure work

#Operator actionSystem action Information requestedDerived or defaultedNecessity gate
15 Wait while setup runs; no additional input on the happy path. Create the unprivileged service identity, private directories, generated config, internal hashing/session keys, SQLite, migrations, and first operator. None. Paths, modes, ports, database location, service user, limits, and internal secrets. Implementation details are not operator decisions.
16 Continue waiting. Install and start the hardened systemd service; obtain the platform certificate; validate Resend; prove direct HTTPS version and security headers. None. ACME contact, systemd unit, and probe URLs come from verified state. Readiness is evidence, not another question.
17 If setup pauses, perform the one printed correction and rerun the same command. Tinkercloud resumes after the last durable successful step and rechecks the failed dependency. Only newly missing state, never prior valid answers. Completed steps and safe answers are reused. Failure must be actionable without becoming a questionnaire.
18 Read the printed dashboard URL and root recovery command; optionally copy them into an operator-owned runbook. Tinkercloud reports ready only after local/public health succeeds. No extra recovery password or remote bypass credential. Root SSH remains the recovery authority. Printing is required; storing a second copy is optional operator practice.

Phase D · First administration

Grant narrow deployment authority

#Operator actionSystem action Information requestedDerived or defaultedNecessity gate
19 Open the dashboard and sign in with the operator email OTP. The platform creates a control-plane session separate from CLI and viewer credentials. Email is prefilled when safe; only the delivered OTP is newly requested. Platform URL and operator identity were established during setup. Remote operator access needs authentication; setup values must not be retyped.
20 Open the global active-deployer allowlist and edit one normalized email per line. Tinkercloud shows the exact current active set and a hidden server revision. Only deployer email addresses the operator intends to authorize. Sorting, normalization, current IDs, statuses, and limits are server-derived. The operator must choose who can deploy; individual status forms are unnecessary ceremony.
21 Confirm only if new/reactivated addresses broaden deployment authority, then save. Tinkercloud atomically creates/reactivates requested deployers, revokes removed deployers’ current credentials, and writes one audit event. One explicit broadening confirmation when applicable. Removal consequences, credential rows, immutable IDs, and app ownership are derived. Broadening must be intentional; narrowing needs no second confirmation. A stale revision rejects everything, refreshes the exact list, and applies no partial change.
22 Later, if the operator requests deployment capability, add their own email to the deployer list. Tinkercloud treats the same person as two separately authorized roles. The operator explicitly chooses this additional role. Operator authority never transfers automatically. Least privilege requires an explicit deployer grant.
23 When an authorized deployer is ready to onboard, copy the displayed platform URL and share it through an existing channel. The deployer requests their own OTP when ready. No invitation email template or second delivery address. The platform URL is already known; an automated invite is optional future convenience. Authorization is the necessary action. Invitation delivery is not.

Phase E · Ongoing operation and recovery

Operate one small server without hidden authority

#Operator actionSystem action Information requestedDerived or defaultedNecessity gate
24 Use dashboard search/status filters and direct-launch controls to inspect apps. Tinkercloud searches current app slug/description locally and launches only the stable protected app origin. Operator authority does not grant app access; the global browser identity, app handoff, and current policy still apply. A search term or filter only when the operator chooses to narrow the list. App URLs, status, description, ownership, and release state are server-derived. Do not ask for an app ID or URL the server already knows.
25 Use dashboard diagnostics or run sudo tinkercloud status/doctor. Inspect service, DNS, TLS, email, disk, database, resource limits, audit, and gateway health. No config path on the standard installation. Canonical paths and hosts come from installed state. Overrides are recovery/test options, not normal questions.
26 Suspend an app or remove a deployer when current access must stop. The next request denies; matching tokens/sessions/live connections are revoked as defined by scope. The selected server-rendered app and explicit app-suspension confirmation. Deployer removal is already expressed by the reviewed exact allowlist and receives no extra confirmation. IDs, storage paths, and affected credentials are server-derived. Immediate revocation is required; internal selectors must never be typed by the operator.
27 Run the signed manual server update when desired. Tinkercloud downloads/verifies, creates bounded local update recovery state, applies, restarts, and runs health plus anonymous-denial probes. An alternate release source only when intentionally overriding the configured source. Installed config, active probe target, and prior binary/state are discovered. Normal update must not require a config path or arbitrary app slug.
28 If remote operator login is unavailable, SSH as root and run the printed recovery command. Root locally changes the operator identity or diagnoses/restarts the service without an HTTP bypass. A replacement operator email only when recovery changes it. Config, database, and service locations are installed-state defaults. Recovery must work without email, but must not create a second remote authority.
29 Boundary: if the VPS is permanently lost, recreate the platform and redeploy replaceable apps. V1 provides no backup or disaster-recovery guarantee. None. No hidden remote replica or recovery claim. Honest loss boundaries are simpler and safer than an unproven backup feature.

Implementation sketch

Wizard state is a resumable projection, not new authority

discover host state
→ ask base domain + operator email
→ derive conventional topology
→ persist validated non-secret progress
→ pause for DNS + Resend ownership
→ ingest secret into root-owned credential boundary
→ generate config + internal keys + database + service
→ prove TLS, email, platform health, route classification, and safe unknown-host denial
→ print dashboard + root recovery

Automation retains strict explicit non-interactive inputs. The human assistant calls the same validation and domain services; it does not create a weaker setup path.

Do or don’t

Build the guided path; keep the explicit automation contract

Do: The assistant removes repeated hostnames, paths, flags, and config editing while preserving the one-server trust model.

Don’t: Do not hide DNS, domain ownership, provider credentials, firewall responsibility, or total-VPS-loss risk. These are necessary external boundaries, not wizard defects.
